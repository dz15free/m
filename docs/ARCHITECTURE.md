# مساعد الأستاذ — وثيقة المنتج والمعمارية التقنية

> **P** · `prof.baczone.app` · النسخة 0.1 (مسودّة للموافقة) · 2026-09-24
>
> «أدخل بياناتك مرة... ودع المنصة تقوم بالباقي.»

هذه الوثيقة هي المرجع قبل كتابة أي سطر برمجي. كل قرار فيها مبرَّر، وكل ما يحتاج قرارًا منك مُعلَّم بـ **❓قرار**.

## 0. ملخّص تنفيذي (صفحة واحدة)

| البند | القرار |
|---|---|
| طبيعة المنتج | **Teacher Workspace** (مكتب الأستاذ الرقمي)، والمكتبة جزء منه لا جوهره |
| الوحدة الأساسية | `TeachingAssignment` = (مؤسسة × سنة × قسم × مادة) — لا `teacher.subject` أبدًا |
| الواجهة | Next.js (App Router) + React + TypeScript + Tailwind، Mobile-first، RTL/LTR |
| البيانات | **مشروع Firebase جديد ومستقل** (Auth + Firestore)، منفصل عن BacZone |
| الملفات | **Cloudflare R2** (خاص + روابط موقّعة قصيرة العمر) — ليس Firebase Storage |
| الاستضافة | **Cloudflare Workers عبر OpenNext** (كما في BacZone، مجاني ويسمح بالاستخدام التجاري)، والكود محمول إلى Vercel/Node دون تعديل |
| OCR | **Tesseract.js داخل المتصفح** + معالجة صورة + محلّل صفوف/أعمدة + مراجعة إلزامية. لا API مدفوع، والصورة لا تغادر الهاتف |
| الدفع | Chargily (نعيد استعمال منطق BacZone المُجرَّب مع إصلاحات) + BaridiMob/CCP يدوي بمراجعة الأدمن |
| الاشتراك | Free للأبد + Trial قابل للضبط + خطط ديناميكية. **لا حذف للبيانات أبدًا**، والانتهاء يُحسب «كسولًا» بلا Cron |

| التكلفة | **0 دج شهريًا** حتى نحو ~1000 أستاذ نشط يوميًا (تقدير)، ثم سنتات يومية |

## 1. فهمي للمنتج

الأستاذ الجزائري اليوم يوزّع عمله بين: دفتر ورقي، ملفات Word من مجموعات Facebook/Telegram، Excel لقوائم التلاميذ، رسائل WhatsApp، وطابعة مقهى الإنترنت. المشكلة ليست «نقص المحتوى» بل **تكرار العمل الإداري**: نفس الأسماء تُكتب في الحضور ثم في كشف النقاط ثم في الوثائق، ونفس بيانات المؤسسة تُكتب في رأس كل وثيقة.

**المنتج = مصدر حقيقة واحد لبيانات الأستاذ، تُبنى عليه كل الأدوات.**

```
                ┌──────────── بيانات تُدخل مرة واحدة ────────────┐
                │ الأستاذ · المؤسسة · السنة · الأقسام · التلاميذ   │
                │ الإسنادات (قسم × مادة) · جدول التوقيت · التوزيع    │
                └──────────────────────┬───────────────────────────┘
          ┌─────────┬─────────┬────────┼─────────┬──────────┬─────────┐
          ▼         ▼         ▼        ▼         ▼          ▼         ▼
       الحضور   دفتر الأستاذ  التقدّم  الوثائق   المعلّقات   التقييم   الإحصائيات
                                              (V2)
```

ما يميّزنا عن مرجع السوق (Sanad) ليس عدد الوثائق بل:
1. **الاستيراد الذكي للتلاميذ** (صورة/PDF/Excel/لصق) — أقوى لحظة «واو» في أول 5 دقائق.
2. **اليوم أولًا**: الشاشة الرئيسية هي «حصص اليوم»، لا قائمة ملفات.
3. **الحضور في 10 ثوانٍ**: «الجميع حاضر» ثم الاستثناءات.
4. **التوزيع المتّصل بالمنجَز**: «أين أنا الآن؟» يُحسب تلقائيًا من دفتر الأستاذ.
5. **الأستاذ متعدد المواد والأقسام** مدعوم من الجذور.

## 2. رؤية المنتج

**الرؤية:** أن يفتح كل أستاذ في الجزائر «مساعد الأستاذ» صباحًا كما يفتح دفتره، وأن يغلقه وقد أنجز عمله الإداري في دقائق.

**الوعد التسويقي:** «كل ما يحتاجه الأستاذ في مكان واحد.»

**مبادئ المنتج (مرتّبة):**
1. **وفّر وقت الأستاذ** — كل ميزة تُقاس بالدقائق المُوفّرة أسبوعيًا.
2. **إذا استطاع النظام فعلها، لا تطلبها من الأستاذ.**
3. **الهاتف أولًا وبيد واحدة** — أهداف لمس ≥ 44px، الإجراءات الأساسية في الثلث السفلي.
4. **لا فشل مسدود** — كل مسار ذكي (OCR) له بديل يدوي بنقرة.
5. **بيانات الأستاذ ملكه** — لا حذف عند انتهاء الاشتراك، وتصدير متاح دائمًا.
6. **خصوصية التلاميذ** — أقل بيانات ممكنة، معالجة الصور محليًا، عزل صارم.

**مؤشرات النجاح (North Star + داعمة):**
- North Star: **عدد الحصص المُسجَّلة أسبوعيًا** (حضور أو درس) — يقيس «الاستعمال اليومي» لا التحميل.
- Activation: أستاذ أنشأ قسمًا + أضاف ≥ 10 تلاميذ + سجّل حضورًا واحدًا خلال 48 ساعة.
- زمن الاستيراد: من فتح «أضف تلاميذك» إلى الاعتماد < 3 دقائق لـ 30 اسمًا.
- التحويل: Trial → Premium.

## 3. شخصيات المستخدمين (Personas)

| الشخصية | الوصف | الاحتياج الأساسي | ما يُقلقها |
|---|---|---|---|
| **أمينة** — معلّمة ابتدائي عامّة | قسم واحد (4AP)، 32 تلميذًا، كل المواد تقريبًا، هاتف Android متوسط، إنترنت متقطّع | الحضور، دفتر اليومي، المذكرات، التوزيع | الوقت، التعقيد، استهلاك الرصيد |
| **كريم** — أستاذ فرنسية في الابتدائي | يدرّس الفرنسية لـ 3AP→5AP في **6–10 أفواج** وأحيانًا مدرستين، أكثر من 200 تلميذ | **الاستيراد السريع**، جدول توقيت معقّد، توزيع لكل مستوى | إدخال مئات الأسماء، الخلط بين الأفواج |
| **سليم** — أستاذ ثانوي (V2) | اقتصاد + محاسبة + قانون، 3AS، 4 أفواج | إسنادات متعددة المواد، علامات، معدلات | ضياع البيانات بين المواد |
| **نادية** — منشئة محتوى (أستاذة فرنسية شريكة) | ترفع fiches وprogressions وaffiches | لوحة رفع سريعة، تصنيف واضح، معاينة | ضياع الحقوق/السرقة |
| **المالك/الأدمن** | يدير الخطط، الدفع اليدوي، المحتوى، الإيرادات | مراجعة الإيصالات بسرعة، رؤية الإيرادات | الاحتيال، الأخطاء المالية |

> ملاحظة سياق: الفرنسية (والإنجليزية منذ 2022) تبدأ في الابتدائي من 3AP ويدرّسها أستاذ مختص متنقّل بين الأفواج. شخصية **كريم** هي أكثر من يحتاج الاستيراد الذكي، ويجب أن تُصمَّم الـ Onboarding لها صراحة.

## 4. رحلات المستخدم (User Journeys)

### 4.1 أول 5 دقائق (Activation)
```
الصفحة الرئيسية ← «ابدأ مجانًا» ← تسجيل (Google أو بريد)
 ← من أنت؟  [معلّم ابتدائي لقسم واحد] [أستاذ مادة لعدة أفواج] [متوسط/ثانوي]
 ← المؤسسة (الولاية ← البلدية ← اسم المدرسة)       ← السنة الدراسية (مقترحة تلقائيًا)
 ← أقسامك (Preset حسب الإجابة الأولى — شاشة واحدة)
 ← أضف تلاميذك (📷/📄/📊/📋/✍️) — قابل للتخطي
 ← جدول التوقيت (شبكة أسبوعية) — قابل للتخطي
 ← «اليوم» : حصص اليوم جاهزة، وزر «تسجيل الحضور»
```
**Presets** (أهم قرار UX في الـ Onboarding):
- *معلّم ابتدائي لقسم واحد*: اختر المستوى + رقم الفوج → يُنشأ قسم واحد مع **كل مواد المستوى** كإسنادات تلقائيًا (قابلة للحذف).
- *أستاذ مادة لعدة أفواج*: اختر المادة → لكل مستوى عدد الأفواج (عدّاد + / −) → تُنشأ `3AP-01, 3AP-02, 4AP-01...` دفعة واحدة، مع إسناد المادة لكل فوج.
- *متوسط/ثانوي*: نفس الأخير مع إمكانية أكثر من مادة (V2 للمحتوى، لكن النموذج جاهز).

### 4.2 الصباح اليومي (Core Loop)
```
فتح التطبيق ← «اليوم»: 08:00 3AP-01 فرنسية (الآن) · 10:00 3AP-02
 ← نقر على الحصة ← شاشة الحصة: [الحضور] [الدرس]
 ← «الجميع حاضر» ← تعديل 2 استثناء ← حفظ تلقائي
 ← تبويب الدرس: اختيار عنصر التوزيع المقترح (التالي تلقائيًا) ← «تمّ» ← ملاحظة اختيارية
 ← التقدّم يُحدَّث: 25/32 (78%)
```

### 4.3 البحث والطباعة
```
بحث: «مذكرة الألوان السنة الثالثة فرنسية» ← نتائج مصنّفة
 ← معاينة ← (Premium؟ ← شاشة ترقية) ← تحميل / طباعة
```

### 4.4 الترقية والدفع
```
شارة Premium على محتوى ← «جرّب مجانًا X أيام» أو «اشترك»
 ← اختيار خطة ← [بطاقة ذهبية/CIB (Chargily)] أو [BaridiMob/CCP]
 Chargily: صفحة الدفع ← عودة ← «جاري التأكيد…» ← مُفعّل (عبر Webhook)
 يدوي: معلومات الحساب + نسخ بنقرة ← رفع الإيصال + رقم العملية ← «قيد المراجعة» ← إشعار عند القبول
```

### 4.5 نهاية السنة (V2)
```
«سنة جديدة 2027/2028» ← ترقية الأقسام: 2AP-01 → 3AP-01
 ← تحديد المعيدين / المغادرين ← إضافة الجدد ← نسخ الإعدادات والتوقيت (اختياري)
```

## 7. التنقّل على الهاتف (Bottom Navigation)

```
┌──────────────────────────────────────────────────┐
│  اليوم   │  أقسامي  │  ( ● الحصة )  │ المكتبة │ المزيد │
└──────────────────────────────────────────────────┘
```
- **اليوم**: حصص اليوم + التقدّم + اختصارات.
- **أقسامي**: الأقسام ← التلاميذ/الحضور/الدروس.
- **الزر المركزي «الحصة»**: يفتح **الحصة الجارية أو التالية مباشرة** (حضور + درس). إن لم توجد حصة اليوم: قائمة سريعة (تسجيل حضور لقسم / إضافة تلاميذ).
- **المكتبة**: بحث + محتوى.
- **المزيد**: التوزيعات، التوقيت، الوثائق، الاشتراك، الإعدادات.

**لماذا لا تبويب «الحضور» مستقل؟** الحضور دائمًا لـ *حصة محددة*؛ تبويب عام يضيف خطوة «اختر القسم». الزر المركزي يعرف الحصة من جدول التوقيت والساعة، فيُسقط خطوتين. سجل الحضور التاريخي يبقى داخل القسم.

**تكلفة القراءة:** وثيقة الأستاذ + وثيقة الجدول + وثائق الأقسام (من الكاش) + وثائق حصص اليوم (≤ 6) ≈ 10 قراءات، وأغلبها من الكاش المحلي في الزيارات اللاحقة.

## 11. تدفّق استيراد التلاميذ (Student Import Flow)

شاشة واحدة، مسار واحد، خمسة مداخل:

```

      لديك قائمة طويلة؟ لا تكتب الأسماء واحدًا واحدًا.
 ┌───────────┬───────────┬──────────┬───────────┬──────────┐
 │📷 صوّر     │🖼 صورة/PDF │📊 Excel  │📋 الصق     │✍️ يدوي    │
 └─────┬─────┴─────┬─────┴────┬─────┴─────┬─────┴────┬─────┘
       ▼           ▼          ▼           ▼          │
   [OCR pipeline] [PDF: نص؟→ استخراج مباشر | ممسوح→OCR]   │
       │           │          │           │          │
       └───────────┴────┬─────┴───────────┘          │
                        ▼                            │
          ImportDraft { rows[], source, warnings }   │
                        ▼                            ▼
         ┌──────── شاشة المراجعة الموحّدة (نفسها للجميع) ────────┐
         │ «تم العثور على 34 تلميذًا» · 31🟢 2🟡 1🔴               │
         │ [⇄ اللقب/الاسم معكوسان؟]  [ترتيب أبجدي] [+ صف]          │
         │ # | اللقب | الاسم | الجنس(اختياري) | الحالة | 🗑          │
         │ تنبيه: «بوجلال آية» مكرّر محتمل مع «بوجلال أية» [دمج]    │
         │ [ اعتماد واستيراد 34 تلميذًا ]                          │
         └────────────────────────────────────────────────────┘
                        ▼
      كتابة Batch واحدة (القسم + ملخّص القائمة) ← رجوع إلى القسم
```

**قواعد:**
- لا شيء يُحفظ قبل «اعتماد». المسودّة تُحفظ في `IndexedDB` محليًا حتى لا تضيع إذا أُغلق التطبيق.
- الفلترة الافتراضية للمراجعة: «يحتاج مراجعة أولًا» — الأستاذ يرى الصفوف 🟡🔴 في الأعلى ويصحّحها فقط.
- تعديل الخلية مباشرة (inline)، بلا نوافذ.
- إذا كان القسم يحتوي تلاميذ: خيار [إضافة إلى الموجودين] أو [استبدال القائمة] مع كشف تكرار مقابل الموجودين.
- **عدة أقسام من مصدر واحد** (مهم لكريم): إذا اكتُشفت عناوين أقسام داخل الملف (أوراق Excel متعددة، أو سطر «القسم: 3 ابتدائي 2»)، نقترح توزيع الصفوف على الأقسام.

## 12. استراتيجية OCR

### 12.1 الاختيار
| الخيار | التكلفة | الخصوصية | الدقة (عربي مطبوع) | القرار |
|---|---|---|---|---|
| **Tesseract.js (WASM) في المتصفح** | 0 | الصورة لا تغادر الجهاز | جيدة للمطبوع الواضح، ضعيفة للمكتوب باليد | ✅ MVP |
| PaddleOCR / ONNX في المتصفح | 0 | ممتازة | أفضل أحيانًا، لكن نماذج أثقل ودعم عربي أقل نضجًا | 🔬 تجربة V2 |
| Google Vision / Azure OCR | مدفوع لكل صورة | الصورة تُرسل لطرف ثالث | ممتازة | ❌ (خيار Premium مستقبلي فقط) |
| LLM Vision (V3) | مدفوع | طرف ثالث | ممتاز حتى للمكتوب باليد | V3 اختياري |

### 12.2 خط المعالجة (كله في Web Worker)
```
1. الإدخال: كاميرا (<input capture>) / صورة / صفحات PDF (pdf.js ← canvas بدقة ~2x)
2. تحسين الصورة (Canvas/OffscreenCanvas):
   • تصغير/تكبير لعرض ~2000px (يكفي للدقة، يحمي الذاكرة على الهواتف الضعيفة)
   • تدرّج رمادي ← تحسين التباين ← عتبة تكيّفية (Sauvola/Bradley)
   • تصحيح الميلان (Deskew) بإسقاط أفقي ← قصّ الحواف
   • (اختياري) أداة قصّ يدوية بأربع زوايا إن كانت الصورة مائلة كثيرًا
3. OCR: Tesseract.js بلغتي `ara+fra` (نماذج tessdata_fast، تُحمّل عند أول استعمال فقط وتُكاش)
   المخرجات: كلمات مع صناديقها (bbox) وثقة كل كلمة — لا نص خام فقط
4. تجميع الصفوف: تجميع الكلمات حسب مركز Y (مع تسامح نسبي لارتفاع السطر)
5. اكتشاف الأعمدة: تجميع حدود X عبر الصفوف (histogram) ← أعمدة مرشّحة
6. تصنيف الأعمدة: رقم تسلسلي (أرقام متزايدة) / تاريخ ميلاد / رقم تسجيل (أرقام طويلة) / نص عربي / نص لاتيني
   ← اختيار عمود(ي) الاسم ← ربط باللقب/الاسم (انظر §12.4)
7. تنظيف: حذف الترويسة (اللقب، الاسم، Nom، Prénom، N°...)، حذف أسطر المجاميع والتواقيع،
   توحيد الحروف (أ/إ/آ→ا للمقارنة فقط، ى/ي، ة/ه، إزالة التشكيل والتطويل)، تصحيح أخطاء OCR الشائعة
8. الثقة لكل صف = دمج (متوسط ثقة الكلمات، طول معقول، حروف من الأبجدية المتوقعة، عدم وجود أرقام داخل الاسم)
   🟢 ≥ 0.85  ·  🟡 0.6–0.85  ·  🔴 < 0.6 أو خلية فارغة
9. كشف التكرار (داخل الدفعة + مع الموجودين): تطابق بعد التوحيد، ثم تشابه Levenshtein/Jaro-Winkler ≥ 0.9
10. عدة صور/صفحات: كل صفحة تمر بالخط كاملًا ← دمج بالترتيب ← إزالة تكرار حواف الصفحات
    ← إعادة الترقيم إن وُجد عمود تسلسل متصل
11. ← شاشة المراجعة الموحّدة (§11)
12. تنظيف: تحرير الـ Bitmaps وإنهاء الـ Worker. **لا رفع ولا تخزين للصورة إطلاقًا.**
```

### 12.3 الأداء على الأجهزة الضعيفة
- تحميل Tesseract (~ 2–4MB WASM + نماذج اللغة) **فقط عند فتح شاشة الاستيراد** (dynamic import)، وتخزينه في Cache Storage عبر Service Worker.
- استضافة ملفات Tesseract والنماذج من أصولنا الثابتة (نفس الدومين) لتفادي الاعتماد على CDN خارجي.
- مؤشر تقدّم لكل صفحة («الصفحة 2 من 3 — 60%») وزر إلغاء.
- ميزانية: صفحة A4 واحدة يجب أن تنتهي في < 15 ثانية على هاتف متوسط؛ نقيس ذلك في Phase 7 على أجهزة حقيقية.

### 12.4 تقسيم الاسم واللقب (خصوصية جزائرية)
- القوائم الإدارية العربية عادةً **«اللقب ثم الاسم»**، والفرنسية `NOM Prénom` (اللقب بحروف كبيرة غالبًا).
- عمودان منفصلان ← مباشرة. عمود واحد «الاسم واللقب» ← نقسّم:
  - لاتيني: الكلمات الكبيرة كليًا = NOM.
  - عربي: الكلمة الأولى لقب، مع دمج البادئات المركّبة للّقب (بن، ابن، آيت، أولاد، بو + كلمة إذا كانت منفصلة، ال...) ومعرفة الأسماء المركّبة (عبد + …، نور الهدى، …الدين، أم …، فاطمة الزهراء). قائمة قابلة للتوسيع في ملف.
- زر عام **«⇄ اللقب والاسم معكوسان»** يصلح القائمة كلها بنقرة، وتعديل فردي لكل صف.
- نحتفظ دائمًا بـ `fullNameRaw` كما قُرئ، لتفادي فقد معلومة بسبب تقسيم خاطئ.

### 12.5 عند الفشل
لا رسالة خطأ تقنية. مثال:
> «تم التعرف على معظم الأسماء، لكن 3 أسماء تحتاج إلى مراجعة.»

وإن كانت الجودة سيئة جدًا (< 50% صفوف صالحة):
> «تعذّر التعرف على بعض البيانات بدقة. جرّب صورة أوضح (إضاءة جيدة، الورقة مستوية)، أو:»
> [ استيراد Excel ] [ لصق القائمة ] [ متابعة وتعديل يدوي ]

ونُبقي ما تم التعرف عليه لتفادي البدء من الصفر.

## 13. استيراد Excel

- المكتبة: **SheetJS** (يدعم `.xlsx` و`.xls` القديم الشائع في الإدارة و`.csv` و`.ods`)، مُحمَّلة ديناميكيًا عند الحاجة فقط. نثبّتها من توزيعها الرسمي (نسخة npm العامة قديمة) — أو `read-excel-file` الأخف إن اكتفينا بـ `.xlsx`. **❓قرار صغير في Phase 7** بعد اختبار ملفات حقيقية.
- الكل في المتصفح، لا رفع للملف.

```
Upload ← قراءة كل الأوراق
 ← اكتشاف صف الترويسة: أول صف يحتوي ≥ 2 من الكلمات المفتاحية
     (رقم|الرقم|N°|No|ر.ت · اللقب|Nom · الاسم|Prénom · الاسم واللقب|Nom et prénom
      · تاريخ الميلاد|Date de naissance · الجنس|Sexe · رقم التسجيل|Matricule ...)
     وإن لم توجد ترويسة: تصنيف الأعمدة بالمحتوى (كما في OCR §12.2-6)
 ← Mapping مقترح (عمود ← حقل) مع قائمة منسدلة لتصحيحه + معاينة أول 5 صفوف
 ← تجاهل الصفوف الفارغة/المجاميع/الخلايا المدموجة
 ← عدة أوراق = عدة أقسام محتملة ← «هل هذه 3 أقسام؟» [نعم، وزّعها] [لا، ورقة واحدة]
 ← شاشة المراجعة الموحّدة
```
Mapping المعتمد يُحفظ محليًا كـ «قالب» لإعادة الاستعمال مع الملف التالي بنفس الشكل.

## 14. استيراد اللصق (Paste)

`<textarea>` كبيرة + المعاينة تتحدّث مباشرة أثناء اللصق (debounce 150ms):

## 15. مخطّط قاعدة البيانات (منطقي)

```
User(1) ──1:1── TeacherProfile
   │
   ├──< School (مؤسسة الأستاذ، 1..n)
   ├──< TeacherYear (سنة دراسية للأستاذ ← يرتبط بـ AcademicYear العامة)
   │        │
   │        ├──< Class (قسم/فوج)  ──< StudentEntry (ضمن roster القسم)
   │        │       │                      └──1:1── StudentProfile (بيانات موسّعة، اختياري)
   │        │       │
   │        ├──< TeachingAssignment (Class × Subject)  ──1:1── ProgressionInstance
   │        ├──1 Schedule (نسخ بتواريخ سريان) ──< Slot → Assignment
   │        └──< Session (حصة فعلية: تاريخ × Slot) { attendance, lessonLog }
   │               └── AttendanceStats (مجمّع لكل قسم)
   │
   ├──1 Entitlement (الخطة الحالية — يكتبها الخادم فقط)
   ├──< Order / Payment / ManualPayment
   └──< Notification

Global (يديرها الأدمن): AcademicYear(+ عطل), Taxonomy(Stages/Levels/Subjects),
Plan, Content, ContentCategory, ProgressionTemplate, DocumentTemplate, Config, AuditLog, Stats
```

**قرارات جوهرية:**
1. **كل بيانات الأستاذ تحت `teachers/{uid}/…`** — العزل يصبح قاعدة واحدة بسيطة وقوية (`request.auth.uid == uid`)، ولا يمكن لأي استعلام خاطئ أن يُرجع بيانات أستاذ آخر.
2. **الـ roster (قائمة التلاميذ المختصرة) داخل وثيقة القسم نفسها** — فتح القسم = **قراءة واحدة** بدل 35. (حد الوثيقة 1MiB يتّسع لآلاف الأسماء؛ القسم ≤ 50.) البيانات الموسّعة للتلميذ (ملاحظات، متابعة) في وثيقة منفصلة تُقرأ فقط عند فتح ملفه.
3. **الحصص افتراضية** — تُحسب من الجدول + الرزنامة؛ الوثيقة تُنشأ فقط عند أول تسجيل.
4. **الحضور = الاستثناءات فقط** داخل وثيقة الحصة.
5. **التلميذ له `id` ثابت** لا يتغيّر عند الترقية (V2) — التاريخ يُربط بالـ id لا بالاسم.
6. **السنة الدراسية ليست hardcoded**: `academicYears/{id}` عامة (يضبطها الأدمن: البداية، النهاية، الفصول، العطل)، وكل أستاذ يرتبط بها ويمكنه إضافة استثناءات محلية (إضراب، عطلة ولائية).

## 18. استراتيجية قواعد الأمان (Firestore Rules)

```js
rules_version = '2';
service cloud.firestore {
  match /databases/{db}/documents {
    function signedIn()   { return request.auth != null; }
    function isOwner(uid) { return signedIn() && request.auth.uid == uid; }
    function isAdmin()    { return signedIn() && request.auth.token.admin == true; }
    function isEditor()   { return isAdmin() || request.auth.token.contentEditor == true; }
    function verified()   { return request.auth.token.email_verified == true
                                 || request.auth.token.firebase.sign_in_provider == 'google.com'; }

    // ── مساحة الأستاذ: عزل تام ──
    match /teachers/{uid} {
      allow read: if isOwner(uid);
      allow create, update: if isOwner(uid) && validTeacher(request.resource.data);
      allow delete: if false;                       // الحذف عبر API مع تأكيد
      match /{sub=**} { allow read, write: if isOwner(uid); }   // + validators لكل مجموعة
    }

    // ── الاشتراك والمال: الخادم وحده يكتب ──
    match /entitlements/{uid} { allow read: if isOwner(uid) || isAdmin(); allow write: if false; }
    match /orders/{id}        { allow read: if isOwner(resource.data.uid) || isAdmin(); allow write: if false; }
    match /payments/{id}      { allow read: if isOwner(resource.data.uid) || isAdmin(); allow write: if false; }
    match /manualPayments/{id} {
      allow read:   if isOwner(resource.data.uid) || isAdmin();
      allow create: if isOwner(request.resource.data.uid) && verified()
                    && request.resource.data.status == 'pending'
                    && request.resource.data.keys().hasOnly([...الحقول المسموحة]);
      allow update, delete: if false;               // المراجعة عبر API (transaction + audit)
    }

    // ── المحتوى ──
    match /contents/{id} {
      allow read:  if resource.data.status == 'published' || isEditor();
      allow write: if isEditor();
    }
    match /{c}/{id} where c in [config, plans, taxonomy, academicYears, ...] { read: all; write: isAdmin }
    match /auditLogs/{id}      { allow read: if isAdmin(); allow write: if false; }
  }
}
```

**مبادئ:**
- **Deny by default**، ثم فتح المسارات صراحةً.
- **Validators** لكل كتابة: الأنواع، الأطوال (اسم ≤ 80 حرفًا)، حجم الـ roster (≤ 60)، القيم المسموحة للحضور (`A|L|E`)، ومنع تعديل حقول النظام (`counters`, `createdAt`).
- **حدود الخطة في القواعد**: إنشاء قسم يتطلّب تحديث `teachers/{uid}.counters.classes` في نفس الـ batch (`getAfter`)، والتحقق أن العدد ≤ `entitlements/{uid}.limits.maxClasses`. قراءة إضافية واحدة فقط عند إنشاء قسم.
- **اختبارات القواعد إلزامية** (Emulator + `@firebase/rules-unit-testing`) — كما يفعل BacZone، وتدخل في CI. سيناريوهات حتمية: أستاذ A لا يقرأ/يكتب أي شيء لأستاذ B؛ لا أحد يكتب `entitlements`؛ لا ترقية ذاتية للأدوار؛ المحتوى غير المنشور مخفي.

## 19. المصادقة (Authentication)

- **Firebase Auth** في **مشروع جديد مستقل** (انظر §45).
- طرق الدخول: **Google** (الأسرع على Android) + **بريد/كلمة مرور** مع تأكيد البريد (مطلوب قبل الدفع اليدوي/Trial لتقليل الإساءة).
- الهاتف (SMS): مؤجّل — مكلف وغير متاح على الخطة المجانية.
- **الأدوار**: Custom Claims (`admin`, `contentEditor`, `finance`) تُضبط بسكربت/‏API أدمن محمي. القواعد تقرؤها من الرمز مجانًا (بلا قراءة قاعدة).
- **التحقق في الخادم**: كل API route تتحقق من `Authorization: Bearer <ID token>` بالتحقق من توقيع JWT محليًا (مكتبة `jose` + مفاتيح Google العامة المُكاشة) — أسرع وأرخص من نداء خارجي لكل طلب، ويعمل على Workers/Vercel/Node.
- الجلسة في الواجهة: Firebase SDK (IndexedDB persistence). لا cookies جلسة في MVP لأن صفحات التطبيق Client-rendered؛ صفحات الأدمن محمية بالقواعد والـ API لا بإخفاء الواجهة.

## 21. منطق الاشتراك (Subscription)

**وثيقة `entitlements/{uid}`** (الخادم وحده يكتبها):
```ts
{
  planId: 'free' | 'premium' | ...,
  status: 'free' | 'trial' | 'active',     // «منتهٍ» لا يُخزَّن — يُحسب
  currentPeriodEnd: Timestamp | null,      // null للمجاني
  limits: { maxClasses, maxAssignments, maxStudentsPerClass },   // لقطة من الخطة لحظة التفعيل
  features: string[],                      // لقطة
  contentAccess: 'free' | 'premium',
  trialUsedAt: Timestamp | null,
  source: 'trial' | 'chargily' | 'manual' | 'admin',
  lastPaymentId?: string,
  updatedAt: Timestamp
}
```

**الانتهاء الكسول (Lazy expiry) — بلا Cron وبلا تكلفة:**
```
effectivePlan(e, now) =
   (e.status in ['trial','active'] && e.currentPeriodEnd > now) ? e : FREE_DEFAULTS
```
- يُطبَّق نفس المنطق في **3 أماكن** من دالة مشتركة: الواجهة (للعرض)، الخادم (توقيع الملفات، الحدود)، والقواعد (`request.time < resource.data.currentPeriodEnd`).
- لا حاجة لمهمة مجدولة تغيّر الحالة عند الانتهاء؛ الحالة المخزّنة «active» مع تاريخ ماضٍ = Free فعليًا.

**التجديد:** `newEnd = max(now, currentPeriodEnd) + plan.durationDays` — التجديد المبكر لا يُضيّع أيامًا.

**ما يحدث عند الانتهاء (❓قرار يحتاج موافقتك):**
- كل البيانات تبقى وتُقرأ وتُصدَّر دائمًا. ✅ (ثابت)
- المحتوى Premium يُغلق. ✅ (ثابت)
- إذا تجاوز الأستاذ حدود Free (مثلًا لديه 6 أقسام والحد 2): **اقتراحي** — كل الأقسام تبقى مرئية، والحضور/الدفتر يعملان في **كل الأقسام الموجودة**، لكن **لا إنشاء لأقسام/إسنادات جديدة** فوق الحد، وتُقفل ميزات Premium (المولّدات المتقدمة، الإحصائيات المتقدمة، المحتوى). السبب: قطع الحضور اليومي يضرّ الثقة أكثر مما يرفع التحويل.

**التذكير قبل الانتهاء:** يُحسب عند فتح التطبيق (بانر «ينتهي اشتراكك خلال 3 أيام») بلا إشعارات مجدولة. البريد التذكيري V2.

## 22. منطق التجربة (Trial)


## 24. تكامل Chargily

### 24.1 ما وجدته في BacZone (يُعاد استعماله)
`src/app/api/chargily/checkout/route.ts` و`webhook/route.ts` في `dz15free/appbaczonedz` تطبيق جيد: `fetch` مباشر بلا حزمة، السعر من القاعدة لا من الطلب، التحقق من التوقيع HMAC-SHA256 على الجسم الخام مع `timingSafeEqual`، سجل طلب قبل الانتقال، وضع test/live من لوحة الأدمن، ومعالجة إعادة الإرسال. **سننقل هذا المنطق** (لا نعيد اختراعه) مع التحسينات أدناه.

### 24.2 التدفق
```
Teacher ─► اختيار خطة ─► POST /api/billing/checkout {planId}   (Authorization: Bearer ID token)
  الخادم: uid من الرمز (لا من الجسم) ← plan من القاعدة (السعر/المدة) ← active؟ ≥ الحد الأدنى؟
       ← حد معدل: ≤ 5 طلبات معلّقة/ساعة/مستخدم
       ← orders/{orderId} = pending (بمعرّف نولّده نحن)
       ← POST Chargily /checkouts { amount, currency:'dzd', success_url, failure_url,
             webhook_endpoint: {SITE_URL}/api/webhooks/chargily, locale, metadata:{orderId, app:'prof'} }
       ← يعيد checkout_url
Teacher ─► Chargily (EDAHABIA / CIB) ─► success_url ─► صفحة «جاري التأكيد» تقرأ orders/{id} (≤ 10 محاولات بفاصل متزايد)
Chargily ─► POST /api/webhooks/chargily
  1. التحقق من التوقيع (header `signature`) على الجسم الخام ← وإلا 403
  2. Transaction:
       webhookEvents/{event.id}.create()  ← إن وُجد: 200 «مُعالَج» (منع التكرار الحقيقي حتى مع التزامن)
       order = orders/{metadata.orderId}  ← غير موجود/مدفوع: 200
       تحقّق: amount == order.amount، currency، mode
       checkout.paid   → order=paid · payments/{id} (gross, fees من الحمولة إن وُجدت, net)
                         · entitlements: تمديد (§21) · stats/revenue_{month} increment
       checkout.failed / checkout.expired → order=failed/expired
  3. خارج الـ transaction: إشعار + auditLog
  4. 200 · (500 عند خطأ مؤقت حتى يعيد Chargily الإرسال)
```

### 24.3 تحسينات مقارنة بـ BacZone
1. **uid من ID token** لا من جسم الطلب (في BacZone يُقبل `uid` من الجسم — انظر §45).
2. **Idempotency ذرّية** عبر `create()` داخل transaction بدل «اقرأ الحالة ثم اكتب» (سباق عند وصول إعادتين معًا).
3. **التحقق من المبلغ** مقابل الطلب.
4. معالجة `failed`/`expired` لتنظيف الطلبات المعلّقة.
5. تسجيل `fees` و`net` إن توفّرت في الحمولة.
6. الوصول للقاعدة بـ **Service Account** (OAuth) لا «سرّ قاعدة البيانات» القديم (مهجور).

**التجديد:** Chargily Pay V2 يعمل بدفعات لمرة واحدة؛ «التجديد» = دفعة جديدة تمدّد الفترة. لا خصم تلقائي متكرر.

## 25. BaridiMob
- في `config/billing.baridimob`: RIP (20 رقمًا) + اسم صاحب الحساب + ملاحظة. زر «نسخ» لكل حقل (Clipboard API) + رمز QR اختياري.
- التعليمات خطوة بخطوة بالعربية: افتح BaridiMob ← تحويل ← الصق RIP ← المبلغ بالضبط ← احفظ لقطة الشاشة.
- **مرجع دفع فريد** يُعرض للأستاذ (مثلًا `P-7K3Q`) ويُطلب كتابته في خانة الملاحظة إن أمكن — يسهّل على الأدمن مطابقة الحوالة.

## 26. CCP
- في `config/billing.ccp`: رقم الحساب + المفتاح + الاسم.
- الدفع عبر شبّاك البريد (صكّ/حوالة) ← تصوير وصل الدفع ← رفعه بنفس المسار.

## 27. سير الدفع اليدوي

```
اختيار خطة ← [BaridiMob | CCP] ← معلومات الدفع + المبلغ (من الخطة) + مرجع الدفع
 ← الأستاذ يدفع ← «رفعت الإيصال»:
     صورة (تُضغط محليًا + SHA-256) ← POST /api/uploads/sign (kind=receipt) ← رفع مباشر إلى R2
     + المبلغ المدفوع، تاريخ الدفع، رقم العملية/الوصل (اختياري)
 ← manualPayments/{id}: status='pending'  (إنشاء من العميل بقواعد صارمة)
 ← واجهة الأستاذ: «قيد المراجعة — عادةً خلال 24 ساعة»
أدمن ← طابور المراجعة (الأقدم أولًا) ← عرض الإيصال (رابط موقّع) + تنبيهات:
        ⚠ المبلغ ≠ سعر الخطة · ⚠ نفس hash لإيصال سابق · ⚠ نفس رقم العملية
 ← [قبول] POST /api/admin/manual-payments/{id}/review {decision:'approve', note}
      Transaction: manualPayment=approved(reviewedBy, reviewedAt, note) · payments/{id} · entitlement تمديد · stats increment
      + auditLog + إشعار «تم تفعيل اشتراكك حتى …»
 ← [رفض] مع سبب إلزامي ← إشعار بالسبب + زر «إعادة الرفع»
```

**حقول `manualPayments/{id}`:** `uid`, `teacherName`, `email` (للعرض في الطابور)، `planId`, `expectedAmount` (من الخطة، يُتحقَّق في القواعد)، `declaredAmount`, `method:'baridimob'|'ccp'`, `paidAt`, `transactionRef?`, `receiptKey`, `receiptHash`, `payRef`, `status:'pending'|'approved'|'rejected'`, `adminNote?`, `reviewedAt?`, `reviewedBy?`, `createdAt`.

## 28. لوحة الإيرادات

| المؤشر | المصدر (بلا مسح شامل) |
|---|---|
| Gross / Fees / Net (شهري، سنوي) | `stats/revenue_{YYYY-MM}` (12 قراءة لسنة) |
| المبيعات حسب الخطة/طريقة الدفع | `byPlan`, `byMethod` في نفس الوثائق |
| الاشتراكات النشطة، Premium، Free، Trials | استعلامات `count()` على `entitlements` (تكلفة ضئيلة لكل 1000 وثيقة مفهرسة) مع شرط `currentPeriodEnd > now` |
| الدفعات اليدوية المعلّقة | `count()` على `manualPayments where status=='pending'` |
| الاشتراكات المنتهية قريبًا | `entitlements where currentPeriodEnd between now and now+7d` |
| سجل تفصيلي | `payments orderBy createdAt desc` بالصفحات + تصدير CSV |

**Fees:** لـ Chargily تُسجَّل من الحمولة إن كانت متاحة وإلا نسبة يضبطها الأدمن في الإعدادات (مُعلَّمة «تقديرية»). الدفع اليدوي: رسوم 0 افتراضيًا مع حقل قابل للتعديل. الواجهة تفصل بوضوح Gross عن Net ولا تسمّي أيًا منهما «ربحًا».

## 30. استراتيجية Offline

| المستوى | المحتوى | المرحلة |
|---|---|---|
| L1 | فتح التطبيق بلا إنترنت (App shell) | MVP |
| L2 | **Firestore persistent cache** (`persistentLocalCache` + multi-tab): آخر بيانات الأقسام/الجدول/الحصص متاحة، و**كتابات الحضور/الدفتر تُصفّ محليًا وتُزامن تلقائيًا** عند عودة الشبكة | MVP |
| L3 | مؤشّر «غير متصل — سيتم الحفظ لاحقًا» + عدّاد العمليات المعلّقة | MVP |
| L4 | تنزيل مسبق لبيانات «اليوم» عند فتح التطبيق، ووضع الأسبوع offline | V2 |

**التعارضات:** وثيقة الحصة تكتب الحقول بمسارات منفصلة (`attendance.{studentId}`) عبر `update` ⇒ دمج على مستوى الحقل بدل استبدال الوثيقة؛ آخر كتابة تفوز لنفس التلميذ — مقبول لأن الأستاذ هو الكاتب الوحيد. عدّادات الإحصائيات تُحدَّث بـ `increment` بالفرق (delta) فتبقى صحيحة حتى مع التزامن المؤجّل.

**تحذير:** iOS Safari قد يمسح التخزين المحلي بعد فترة خمول طويلة؛ الكتابات المعلّقة قد تضيع إن لم يُفتح التطبيق مع الإنترنت قبل ذلك. نوضّح هذا بمؤشر «X عمليات لم تُرسل بعد».

## 31. تعدّد اللغات (i18n)

- مكتبة: **`next-intl`** (ناضجة مع App Router، رسائل ICU للجمع/الأعداد).
- لغة الواجهة **بلا بادئة URL** (`/app` لا `/ar/app`) — تُخزَّن في `teachers/{uid}.uiLocale` + cookie؛ الصفحات العامة (Landing) تدعم `/fr` لاحقًا لأجل SEO.
- الرسائل في `messages/ar.json` و`messages/fr.json` مقسّمة بمساحات أسماء لكل ميزة (`attendance.*`, `import.*`) — لا نص مكتوب داخل المكوّنات.
- **لغة الواجهة ≠ لغة المحتوى**: أستاذ الفرنسية قد يختار واجهة عربية ومحتوى فرنسي. كل كتلة محتوى تأخذ `lang` و`dir` الخاصين بها (`dir="auto"` للأسماء المختلطة).
- CSS بخصائص منطقية فقط (`ms-*`, `me-*`, `ps-*`, `start-*`) — لا `left/right`. الأيقونات الاتجاهية (أسهم) تنعكس تلقائيًا.
- الأرقام: أرقام لاتينية 0-9 (الشائعة في الجزائر) حتى في الواجهة العربية؛ التاريخ `dd/MM/yyyy`؛ أسماء الأشهر الجزائرية (جانفي، فيفري، مارس، أفريل، ماي، جوان، جويلية، أوت، سبتمبر، أكتوبر، نوفمبر، ديسمبر) عبر قاموس خاص لأن `Intl` يعطي أسماء المشرق.
- مسرد مصطلحات موحّد (glossary.md) يراجعه أستاذ: «القسم/الفوج»، «التوزيع السنوي»، «المذكرة»، «دفتر النصوص/دفتر الأستاذ»، «الحصة»، «الغياب المبرّر».

- **`repo.ts` هو المكان الوحيد الذي يستدعي Firestore** لكل ميزة ⇒ الانتقال مستقبلًا إلى قاعدة أخرى (Postgres/Supabase) يمس هذه الملفات فقط، لا المكوّنات. هذا هو «الـ Portability» الحقيقي.
- **`lib/server` محمي بـ `server-only`** ⇒ خطأ بناء إن استُورد في الواجهة (لا تسريب أسرار).
- **`shared/`** لمنطق يجب أن يتطابق في الواجهة والخادم (الاشتراك، المخططات).
- لا مجلد `services/` أو `hooks/` عام يتضخّم؛ كل شيء قرب ميزته.

## 45. BacZone — ما وجدته وما نعيد استعماله

فحصتُ `dz15free/appbaczonedz` (قراءة فقط، لم أغيّر فيه شيئًا). الملف `code of the platform.txt` في هذا المستودع هو نسخة قديمة أحادية الملف (StudyLink) من BacZone، ولا يُعاد استعماله.

**الموجود:**
- Next.js 15 + React 19 + TypeScript + Tailwind 3 + Zustand + TanStack Query.
- Firebase: **Auth + Realtime Database** (باقة Spark) — لا Firestore فعليًا.
- النشر: **Cloudflare Workers عبر OpenNext** (`wrangler.toml`)، وليس Vercel.
- Backend: Route Handlers داخل Next (`/api/chargily/checkout`, `/api/chargily/webhook`, push, AI...).
- الوصول من الخادم للقاعدة: REST + «سرّ قاعدة البيانات» القديم (`FIREBASE_DB_SECRET`).
- التحقق من الهوية في الخادم: `verifyFirebaseIdToken` عبر Identity Toolkit (`accounts:lookup`).
- **Chargily**: تكامل جيد (انظر §24.1) + عمولة الأساتذة + وضع test/live من الإعدادات.
- الملفات: Base64 داخل RTDB + Google Drive.
- PWA: `manifest.json` + `sw.js` يدوي + Web Push (VAPID).
- اختبارات قواعد بالـ Emulator.

**القرار:**
| العنصر | إعادة استعمال؟ |
|---|---|
| حساب Cloudflare + الدومين + أسلوب النشر OpenNext | ✅ نفس الحساب، Worker منفصل |
| منطق Chargily (checkout/webhook/التحقق) | ✅ نقل مع التحسينات (§24.3) — **نفس حساب التاجر في Chargily** مع `metadata.app='prof'` ومسار webhook خاص بـ prof |
| أنماط الكود (Zod، server-only، اختبارات القواعد، sw يدوي) | ✅ |
| مشروع Firebase (`studylinkchatapp`) | ❌ **مشروع جديد** للأسباب: (1) بيانات قُصّر تستحق عزلًا تامًا عن مجتمع عام، (2) حصص Spark منفصلة (نشاط BacZone لا يستهلك حصة prof)، (3) نحتاج Firestore بقواعد جديدة، (4) أمان: في BacZone عقدة `users` مقروءة لكل مستخدم مسجّل |
| تخزين Base64/Drive | ❌ → R2 |
| حسابات المستخدمين المشتركة (SSO) | ❌ الآن (جمهور مختلف)؛ ممكن لاحقًا عبر Identity Platform/‏custom tokens إن ظهرت حاجة |

**ملاحظات أمنية على BacZone (للعلم؛ لم أعدّل شيئًا هناك):**
1. `/api/chargily/checkout` يقبل `uid` من جسم الطلب بلا تحقق من رمز الهوية ⇒ يمكن لأي شخص إنشاء طلب دفع باسم مستخدم آخر (الأثر محدود لأن الدافع هو من يدفع، لكنه يسمح بإهداء غير مقصود/تلويث السجلات). الحل: `verifyFirebaseIdToken` الموجود أصلًا.
2. قاعدة `users: ".read": "auth != null"` مع فهرسة `email` ⇒ أي مستخدم مسجّل يستطيع قراءة بريد وبيانات كل المستخدمين. يستحق فصل البيانات العامة عن الخاصة.
3. الـ webhook يفحص `status === 'paid'` ثم يكتب في خطوات منفصلة ⇒ إعادتان متزامنتان قد تُعالَجان معًا (المنح نفسه idempotent لكن سجل المبيعات قد يتكرر).
4. «أسرار قاعدة البيانات» (Database secrets) مهجورة من Google؛ يُفضّل Service Account.

أستطيع إصلاحها في BacZone في مهمة منفصلة إن أردت (هذه الجلسة لديها صلاحية قراءة فقط على ذلك المستودع).

## 46. معالجة الأخطاء (مبدأ)

طبقة واحدة `toUserMessage(error)` تحوّل رموز Firebase/الشبكة/الـ API إلى رسائل مفهومة من ملفات i18n:
| الرمز | الرسالة |
|---|---|
| `permission-denied` | ليس لديك صلاحية للوصول إلى هذا المحتوى. |
| `unavailable` / offline | أنت غير متصل. سيتم حفظ التغييرات عند عودة الإنترنت. |
| `resource-exhausted` | الخدمة مشغولة حاليًا، حاول بعد قليل. |
| Premium مطلوب | هذا المحتوى متاح في الاشتراك المميّز. [جرّب مجانًا] |
| OCR جزئي | تم التعرف على معظم الأسماء، لكن 3 أسماء تحتاج إلى مراجعة. |

والتفاصيل التقنية تُسجَّل (console في التطوير، سجل الخادم في الإنتاج) ولا تُعرض.
